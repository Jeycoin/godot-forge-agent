# 开源对标与架构迭代记录

## 1. 结论

GodotForge 不是 OpenHands、Aider 或 SWE-agent 的替代品，它聚焦 **Godot 游戏原型的契约式生成与真实引擎验证**。v1.0 的技术方向并不落后：LangGraph 持久化状态图、结构化模型输出、人工审批、真实 Headless 验证和有界修复都是合理设计。

但它与成熟开源项目的主要差距也很明确：v1.0 更像一个设计良好的学习原型，而不是通用编码平台。差距集中在工程契约、变更审查、验证分层、代码库理解、执行沙箱和评估规模，而不是“是否需要再换一个模型”。

## 2. 参考的开源项目

| 项目 | 可学习的设计 | 对本项目的启发 |
|---|---|---|
| [LangGraph](https://github.com/langchain-ai/langgraph) | Durable Execution、Human-in-the-loop、状态与轨迹观测 | 保留状态图、checkpointer 和 interrupt，不另造工作流引擎 |
| [OpenHands](https://github.com/OpenHands/OpenHands) | 独立运行时、Docker 沙箱、按会话隔离工作区 | 当前本机执行不是完整安全边界，真实部署必须增加沙箱 |
| [Aider](https://github.com/Aider-AI/aider) | 代码库地图、Git diff/undo、自动 lint/test 和修复 | 审批应展示真实 diff；每次修改后必须执行可重复验证 |
| [SWE-agent](https://github.com/SWE-agent/SWE-agent) | Agent-Computer Interface、简单工具链、配置化与基准评估 | 工具接口应稳定、可测试；不要用复杂框架替代有效反馈 |
| [Godot MCP](https://github.com/Coding-Solo/godot-mcp) | 启动编辑器、运行项目、捕获日志、场景操作 | 后续可从 Headless CLI 扩展到编辑器与场景级工具 |

以上用于学习架构思路，不表示本项目依赖或集成了这些项目的全部代码。

## 3. v1.0 的合理之处

- 使用 LangGraph 管理并行、循环、审批和恢复，场景匹配度高。
- 模型输出使用 Pydantic 约束，而不是把自由文本直接当代码执行。
- 人工审批前不写入文件，拒绝后不会启动引擎。
- 文件路径有白名单，写入有临时文件替换和批次失败恢复。
- 验证同时要求进程退出码和 `SMOKE_TEST_OK`，避免“进程没崩溃就算成功”。
- 修复有次数上限，保留失败结果，不通过删除测试制造成功。
- DeepSeek 已跑通过真实在线生成与 Godot 验证链路。

## 4. v1.0 的具体不足

### 4.1 多 Agent 只靠提示词分工

原来的计划只有任务名和文件列表，角色所有权写在开发提示词中。模型可能越权生成同一文件，公共方法、信号和属性也没有显式契约。

### 4.2 并行是固定角色列表

`fan_out` 写死 gameplay、scene、interface，计划节点无法真正决定并行模块。虽然使用了 `Send`，但数据驱动程度不够。

### 4.3 验证只有一个阶段

直接运行主场景会把资源导入、脚本解析和玩法初始化混在一起，错误定位不够清晰，也不符合“先构建/检查，再运行测试”的工程习惯。

### 4.4 人工审批信息不足

只展示文件名和字节数，审批人无法判断实际修改内容，也无法确认产物是否与当前文件一致。

### 4.5 仍未覆盖成熟通用编码平台能力

- 没有大型代码库 repo map、符号索引和依赖图。
- 没有 Git worktree、提交和基于提交的恢复。
- 没有容器级文件、网络、CPU 和内存隔离。
- 没有 Godot 编辑器插件或 MCP 场景工具。
- 评估集规模较小，不能据此声称普遍生成成功率。

## 5. v1.1 已完成的迭代

| 改进 | 实现 | 价值 |
|---|---|---|
| 模块契约 | `ModuleContract` 声明职责、文件所有权和公共接口 | 多 Agent 共享同一份协作约束 |
| 数据驱动并行 | `fan_out` 遍历 `plan.modules` 生成 `Send` | 计划真正决定并行拓扑 |
| 确定性所有权审查 | 集成时记录 owner，审查时核对计划中的 owned_paths | 越权和契约冲突不再只依赖模型自觉 |
| 契约感知修复 | 修复补丁重新绑定 owner，区分全量重建与局部补丁 | 减少修复造成的接口和文件丢失 |
| 双阶段引擎验证 | 先执行 Godot Import/解析，再执行 Smoke Test | 错误分类更清晰，结果可逐阶段追踪 |
| 结构化阶段结果 | `ValidationStageResult` 保存命令、退出码、日志、错误和耗时 | 提升验证可观测性 |
| 真实 diff 审批 | 审批包含 create/update、SHA-256 和 unified diff | 人工审批从文件清单升级为内容审查 |
| 回归测试 | 新增契约、越权修复、diff 和双阶段验证测试 | 防止架构升级后行为退化 |

关键代码：

- `src/godot_forge/schemas.py`：`ModuleContract`、`ValidationStageResult`
- `src/godot_forge/models.py`：契约生成与契约驱动开发提示
- `src/godot_forge/nodes.py`：动态派发、所有权审查、diff 审批和修复合并
- `src/godot_forge/workspace.py`：diff、哈希、双阶段 Godot 验证
- `tests/test_contracts.py`、`tests/test_preview.py`：新增架构回归测试

## 6. 后续迭代优先级

### P0：不可信代码的执行沙箱

当前路径白名单和危险函数检查不能阻止所有 GDScript 系统能力。真实开放服务应使用容器或受限虚拟机，挂载最小工作区，禁用或限制网络，并设置 CPU、内存、进程数和超时。

### P1：Git 与大型工程理解

引入 Git worktree 隔离每次构建，用提交和 diff 管理变更；对已有大型项目增加文件清单、符号索引、依赖图和按需读取，避免把整个代码库塞入提示词。

### P1：Godot 编辑器与场景工具

参考 Godot MCP 增加编辑器启动、场景读取、节点操作、截图和调试日志工具。MCP 是工具协议，不替代 LangGraph 的状态控制；两者可以组合。

### P1：更有统计意义的评估

扩充不同玩法和复杂度需求，记录首次通过率、修复成功率、人工接管率、Token 成本、延迟和失败类型，并重复运行以降低随机性。

### P2：服务化增强

增加异步任务队列、取消、并发限制、用户认证和租户隔离。只有出现真实部署需求后再引入这些基础设施，避免学习项目过度设计。

## 7. 不建议盲目跟风的方向

- 不为了“看起来先进”把单机原型拆成微服务。
- 不在小型本地知识库上强行引入向量数据库集群。
- 不把 MCP、LangGraph 和模型框架重复堆叠成同一层。
- 不用模型评分替代 Godot 的真实运行断言。
- 不用单次 DeepSeek 成功结果宣称通用生成能力。
