# GodotForge 项目学习文档

## 1. 学习目标

学完本项目，应能独立解释并实现：

1. 用 LangGraph 构建带并行、循环、审批和持久化的 Agent。
2. 用 Pydantic 和 JSON Schema 约束 DeepSeek 等模型的结构化输出。
3. 用模块契约降低多 Agent 并行开发的冲突。
4. 用 RAG 为代码生成提供 Godot 4 版本化知识。
5. 用安全工作区、diff 审批和原子写入控制文件修改。
6. 用真实 Godot Import 与 Smoke Test 验证生成结果。
7. 用有界修复和自动化测试提高系统可靠性。

建议具备 Python 基础、基本 HTTP 知识和少量 GDScript 阅读能力。不要求先掌握所有 LangChain API。

## 2. 从业务问题理解项目

Game Jam 原型开发通常包含需求收敛、玩法实现、场景组装、UI、运行验证和修复。普通代码生成只覆盖“写代码”，GodotForge 覆盖完整交付链路：

```text
需求 → 契约 → 并行实现 → 集成审查 → 人工确认 → 写入
     → Import → Smoke Test → 修复或交付
```

核心思想是：**模型负责生成建议，确定性程序负责权限、状态和验收。**

## 3. 代码阅读顺序

| 顺序 | 文件 | 重点 |
|---|---|---|
| 1 | `src/godot_forge/schemas.py` | 理解系统传递的数据结构 |
| 2 | `src/godot_forge/state.py` | 理解 LangGraph 状态与 reducer |
| 3 | `src/godot_forge/graph.py` | 理解节点、边和修复闭环 |
| 4 | `src/godot_forge/nodes.py` | 理解每个业务步骤 |
| 5 | `src/godot_forge/models.py` | 理解离线模型与真实模型适配 |
| 6 | `src/godot_forge/workspace.py` | 理解 diff、写入与引擎验证 |
| 7 | `src/godot_forge/runtime.py` | 理解 thread_id、审批恢复和 API 边界 |
| 8 | `tests/` | 从断言理解系统必须满足的不变量 |

不要一开始就逐行阅读模板中的游戏代码；先掌握 Agent 架构，再阅读 `templates.py`。

## 4. 核心数据模型

### 4.1 GameSpec

`GameSpec` 将自然语言收敛为标题、类型、描述、机制、操作和视觉风格。它的作用是减少后续节点的歧义，而不是保存一段更漂亮的自然语言。

### 4.2 ModuleContract

v1.1 的核心结构：

```json
{
  "name": "gameplay",
  "responsibility": "玩家移动、生命值和敌人追踪",
  "owned_paths": ["scripts/player.gd", "scripts/enemy.gd"],
  "public_interfaces": [
    "SurvivorPlayer.take_damage(amount: int)",
    "SurvivorPlayer.died: Signal"
  ]
}
```

- `owned_paths` 回答“这个 Agent 可以写哪些文件”。
- `public_interfaces` 回答“其他 Agent 可以依赖哪些方法、信号和属性”。
- `responsibility` 回答“实现什么业务职责”。

审查节点会检查实际 owner 是否符合计划，提示词不再是唯一约束。

### 4.3 FileChange 与 ArtifactBundle

`FileChange` 表示一个完整文件修改，包含路径、内容、用途和负责人。`ArtifactBundle` 是一个角色的产物集合。

修复时：

- `replace_all=false`：按路径合并局部补丁，保留未修改文件。
- `replace_all=true`：用完整新产物替换旧集合，适用于离线参考实现的全量重建。

### 4.4 VerificationResult

总结果包含状态、日志、错误、耗时和 `stages`。每个阶段又保存自己的命令、退出码、输出和错误，便于区分导入失败与玩法测试失败。

## 5. LangGraph 状态与控制流

### 5.1 状态 Reducer

`ForgeState` 中：

```python
artifacts: Annotated[list[dict[str, Any]], operator.add]
trace: Annotated[list[dict[str, Any]], operator.add]
```

多个并行开发节点分别返回增量列表，LangGraph 用 `operator.add` 聚合。普通字段如 `plan`、`verification` 则使用后写覆盖。

学习重点：并行节点不应共同修改一个可变列表；它们只返回自己的增量，由 reducer 合并。

### 5.2 Send 动态并行

`fan_out` 遍历 `plan.modules`，每个模块生成一个 `Send("develop", ...)`。因此并行拓扑来自计划数据，而不是在图里写死三个函数调用。

### 5.3 条件边与有界循环

- 静态审查失败：`review → repair → review`
- 引擎验证失败：`verify → repair → review`
- 审查通过但未授权：`review → approval`
- 已授权的修复版本：`review → apply`

`repair_count` 和 `max_repairs` 防止无限修复。达到上限后保留失败结果并结束。

### 5.4 interrupt 与 Checkpointer

审批节点通过 `interrupt` 返回模块契约、文件清单和 diff。SQLite checkpointer 保存当前状态。批准或拒绝后，使用同一 `thread_id` 调用：

```python
Command(resume={"approved": True, "note": "确认变更"})
```

进程重启后仍能恢复，因为文件内容、计划和授权状态都在检查点中。

## 6. DeepSeek 与结构化输出

### 6.1 适配层

`OpenAIGodotModel` 实际承担 OpenAI 兼容适配器职责。DeepSeek 自动使用：

- 模型：`deepseek-chat`
- Base URL：`https://api.deepseek.com/v1`
- 输出：`json_mode`

### 6.2 为什么显式注入 JSON Schema

仅要求模型“输出 JSON”不能保证字段正确。JSON 模式下，适配层将 `schema.model_json_schema()` 放入系统提示，再使用 `include_raw=True` 同时保留原始响应和解析结果。

解析失败时报告 schema 名、finish reason 和解析错误，避免把空结果直接交给后续节点。

### 6.3 为什么不把模型输出当可信命令

模型只产生 `FileChange` 建议。真正的路径权限、owner、危险调用、审批、写入和运行判断由 Python 代码执行。提示词是协作约束，不是安全边界。

## 7. RAG 检索

`retrieval.py` 使用中文分词和 BM25 检索本地 Godot 4 文档，覆盖工程结构、物理移动、信号、UI、Headless 和安全约束。

本项目 RAG 的目的不是“让回答更丰富”，而是减少 Godot 3/4 API 混用，并把测试协议传给开发和修复节点。最终正确性仍由真实引擎验证。

可扩展方向：按 Godot 版本和模块 topic 过滤、引用官方文档、建立检索召回评估，而不是一开始引入复杂向量集群。

## 8. 安全工作区与变更审批

### 8.1 路径约束

`validate_relative_path` 拒绝绝对路径、反斜杠和 `..`，只允许：

- `project.godot`
- `README.md`
- `scripts/*.gd`
- `scenes/*.tscn`

写入前再次使用 `resolve` 和 `is_relative_to` 检查目标没有逃逸工作区。

### 8.2 Diff 审批

`WorkspaceManager.preview` 对比已有文件与新内容，返回：

- `create` 或 `update`
- 内容 SHA-256
- unified diff
- 文件 owner

这让审批者能审查内容，而不是只批准一串文件名。

### 8.3 原子写入与恢复

每个文件先写临时文件再替换。批处理中途失败时，根据备份恢复已处理文件。它保证本地批次的失败恢复，不等同于分布式事务。

### 8.4 安全边界

本项目不是完整代码沙箱。不可信 GDScript 仍可能使用其他系统 API。开放部署必须使用容器或虚拟机、资源限制、网络隔离和最小权限挂载。

## 9. Godot 双阶段验证

### 9.1 Import 阶段

```bash
godot --headless --editor --path <workspace> --quit
```

用于发现资源导入、脚本解析和类型加载问题。退出码必须正常，日志不能包含错误标记。

### 9.2 Smoke Test 阶段

```bash
godot --headless --path <workspace> --quit-after 120 -- --smoke-test
```

游戏主脚本识别 `--smoke-test`，检查玩家、敌人、HUD 和游戏循环。成功必须输出 `SMOKE_TEST_OK` 并以 0 退出。

`--quit-after` 是帧数兜底，防止错误脚本永久运行。成功标记与退出码缺一不可。

### 9.3 为什么不用模型评价替代运行

“代码看起来正确”无法发现类型解析、场景路径、节点初始化和帧时序问题。真实引擎反馈是该项目最重要的质量门禁。

## 10. 测试策略

测试分层如下：

- 单元测试：路径、diff、模型配置、检索。
- 工作流测试：并行、审批、拒绝、修复、SQLite 恢复。
- 对抗测试：路径穿越、模块越权、连续静态失败、部分补丁。
- API 测试：创建、查询和审批恢复。
- 引擎测试：真实 Godot Import 与 Smoke Test。
- 在线测试：显式开启后运行 DeepSeek 全链路，默认跳过。

运行：

```bash
.venv/Scripts/python.exe -m ruff check .
.venv/Scripts/python.exe -m pytest
```

测试的价值不是数量，而是验证关键不变量，例如“审批前零写入”和“非法路径永远不会进入文件系统”。

## 11. 动手练习

### 练习一：修改玩家速度

修改 `templates.py` 中 `SPEED`，运行完整测试并观察真实 Godot 验证。理解模板生成与 Agent 工作流的区别。

### 练习二：制造模块越权

阅读 `tests/test_contracts.py`，让 gameplay 修改 HUD 文件，观察审查反馈和修复轨迹。

### 练习三：验证局部补丁合并

阅读 `tests/test_repair.py`，解释为什么 `replace_all=false` 时必须保留未修改文件。

### 练习四：模拟引擎失败

使用 `FakeRunner` 第一次返回错误、第二次返回成功，观察 `verify → repair → review → apply → verify`。

### 练习五：验证断点恢复

运行 `test_sqlite_checkpoint_resumes_after_runtime_restart`，说明为什么新运行时能从同一个 `thread_id` 继续。

### 练习六：增加一个玩法断言

在生成的 `main.gd` 冒烟测试中增加“敌人确实发生位置变化”的断言，再运行真实引擎测试。注意需要等待足够物理帧。

## 12. 推荐学习顺序

1. 先跑通离线 Demo 和测试。
2. 阅读 schemas、state、graph，画出节点与状态流。
3. 阅读 nodes，理解契约、审批和修复。
4. 阅读 workspace，理解真实工具反馈。
5. 阅读 models，理解 DeepSeek 与 JSON Schema。
6. 完成动手练习，再考虑 Git、MCP 或沙箱扩展。

不要按“安装更多框架”的方式学习。每增加一个组件，都应能回答它解决了什么可验证的问题。
